# Тренажёр английского — документация разработчика

Локальный тренажёр перевода «русское предложение → английский» на основе дампа
Tatoeba. Публикуется как статический сайт (PWA) на GitHub Pages.

- Приложение-фронтенд: `index.html`, `styles.css`, `app.js`, `sw.js`
- Данные: `data/` (собираются скриптом `tools/build_index.py`)
- Локальный линтер harper.js: `vendor/harper/`
- Руководство пользователя: `guide.html`

---

## 1. Общая архитектура

Приложение полностью статическое: никакого сервера или сетевого API для
основного сценария. Всё, что нужно для поиска предложений, хранится локально
в репозитории и раздаётся GitHub Pages.

Данные разбиты на **чанки** (несколько сотен небольших файлов вместо пяти
монолитных), поэтому клиент качает только то, что нужно для текущего поиска:
один файл инвертированного индекса на первую букву запроса и 1–3 пакета
предложений (см. §2, §3).

```
index.html ──→ app.js ──→ data/manifest.json (список чанков)
                   │           ├── data/widx/widx_<char>.json    (индекс по букве)
                   │           ├── data/packs/pack_<bucket>.json (предложения по id)
                   │           └── data/ru/ru_<bucket>.jsonl     (русские по id)
                   ├── translate.googleapis.com   (машинный перевод, запасной)
                   ├── api.mymemory.translated.net (резервный перевод)
                   ├── api.tatoeba.org/v1/audios/{id}/file  (аудио носителя)
                   └── vendor/harper/              (проверка грамматики, WASM)
```

Поток пользователя:

1. Ввод слова → загрузка `widx_<буква>.json`, пересечение списков → кандидаты.
2. Кандидаты группируются по бакетам id; пакеты самых наполненных бакетов
   скачиваются по одному (до `MAX_PACKS_PER_SEARCH`, см. §4.3).
3. Получение списка кандидатов-предложений; перемешивание по тиру; постраничное
   пополнение в пул (пагинация «Следующее предложение»).
4. Каждое предложение показывается как «русский текст → напиши английский».
5. Ответ сравнивается с эталоном (нормализация) и проверяется линтером harper.js.
6. Воспроизводится аудио носителя (с пессимистичным fallback-перебором записей).

Фронтенд не знает о существовании исходных дампов: для него есть только
манифест и файлы чанков.

## 2. Пайплайн сборки данных (`tools/build_index.py`)

Скрипт ничего не делает на клиенте. Он запускается один раз (локально,
на машине разработчика) и генерирует содержимое каталога `data/`, которое
коммитится в репозиторий.

Требование: **Python 3** (Node.js не требуется).

### 2.1 Запуск

```
python tools/build_index.py [--limit N] [--dump-dir DIR] [--out DIR] [--skip-download] [--chunk-size N]
```

- `--limit N` — режим теста: обработать не более N строк каждого дампа.
- `--dump-dir DIR` — куда скачивать/откуда читать `.bz2` (по умолчанию
  `%TEMP%\kilo\tatoeba_dumps`).
- `--out DIR` — каталог результата (по умолчанию `data`).
- `--skip-download` — не скачивать, использовать уже лежащие дампы.
- `--chunk-size N` — размер бакета id (по умолчанию 100000).

Выход из процесса: `0` — успех, `1` — ошибка/нет файлов, `2` — самый большой
файл результата превысил лимит GitHub Pages (100 МиБ).

### 2.2 Источники (дампы)

Скачиваются с `https://downloads.tatoeba.org/exports/per_language/`:

| Файл в дампе                       | Каталог | Назначение                                |
|------------------------------------|---------|-------------------------------------------|
| `eng_sentences.tsv.bz2`            | `eng/`  | английские предложения `id \tab lang \tab text` |
| `rus_sentences.tsv.bz2`            | `rus/`  | русские предложения                      |
| `eng-rus_links.tsv.bz2`            | `eng/`  | пары связей `id_eng \tab id_rus` (обе стороны) |
| `eng_sentences_with_audio.tsv.bz2` | `eng/`  | `sentence_id \tab audio_id \tab user \tab license \tab url` |

Скачивание идемпотентное: если файл уже лежит в `dump-dir` и непустой —
пропускается (записывается через `.part` + атомарный `os.replace`).

### 2.3 Алгоритм построения

По шагам:

1. **Загрузка английских предложений.** Для каждой строки: `w = len(text.split())`.
   В базу попадают только предложения с **1 ≤ w ≤ 20** словами (разумный
   размер для тренажёра, экономия места). Ключ `sid` → текст и число слов.

2. **Загрузка русских предложений.** Все непустые строки дампа `rus`.
   Ключ `sid` → текст.

3. **Загрузка аудио.** Группировка по предложению: `sid → [audio_id, ...]`.
   У одного предложения может быть несколько записей произношения.
   Лицензия **не фильтруется** (по требованию пользователя — включаются
   все записи без разбора).

4. **Фильтр «с аудио».** `kept_ids = {sid | sid ∈ eng_text и sid ∈ audio_raw}`:
   дальше работаем только с английскими предложениями, у которых есть хотя
   бы одна аудиозапись. Это ключевой критерий качества: каждое предложение
   в тренажёре обязательно озвучено.

5. **Загрузка связей.** Файл связей бинаправленный, поэтому обе пары
   ориентации пробуются: если `a` — английское, а `b` — русское, то
   `links[a].add(b)`; иначе, если наоборот, `links[b].add(a)`. Связи, где
   язык не совпал ни с одним загруженным предложением, отбрасываются.

6. **Финальные множества.**
   - `kept_links`: связи только для `kept_ids` (английское предложение с аудио).
   - `kept_audio`: `sid → [audio_id,...]` для `kept_ids`.
   - `referenced_ru`: множество русских `sid`, на которые ссылаются `kept_links`
     (только они попадут в `ru.jsonl` — русские предложения, к которым никто
     не ведёт, не нужны).

7. **Построение словесного индекса** (`wordidx`):
   ```
   для каждого sid из kept_ids:
       для каждого токена из set(tokenize_key(eng_text[sid])):
           wordidx[tok].add(sid)
   ```
   Использование `set()` по токенам предложения убирает дубликаты слов в
   одном предложении (например, «to be or not to be» добавляет id один раз).

8. **Сериализация** в чанки:
   - **widx**: инвертированный индекс разбивается по первой букве токена —
     файл `widx_<char>.json` на символ (`a`…`z`, `0`…`9`). Токены
     сортируются (детерминированный вывод).
   - **packs**: `kept_ids` группируются по `sid // chunk`; каждый бакет
     записывается как `pack_<bucket>.json`:
     `{ "engId": {"t": текст, "a": [audio_ids], "l": [ru_ids]}, ... }`.
   - **ru**: `referenced_ru` группируются по `rid // chunk`; каждый бакет —
     `ru_<bucket>.jsonl` (JSON Lines, `{"id":N,"t":"..."}`).
   - **manifest**: `data/manifest.json` — версия сборки, общий `chunk`,
     списки существующих файлов (`widx`, `packs`, `ru`) и статистика.

### 2.4 Токенизация Python (`tokenize_key`)

```python
norm = unicodedata.normalize("NFKC", text).lower()
[t.strip("'") for t in re.findall(r"[0-9a-z']+", norm) if t.strip("'")]
```

- NFKC-нормализация (полуширина/полноширина, лигатуры) + lower-case,
- регулярка выделяет последовательности `[0-9a-z']+`,
- крайние апострофы удаляются (чтобы `'hello` и `hello` совпадали).

Этот алгоритм **должен совпадать** с клиентским `tokenizeQuery` в `app.js`
(см. §4.1), иначе индекс и запрос начнут расходиться.

### 2.5 Лимиты

- `HARD_LIMIT = 100 МиБ` — после сборки проверяется самый большой файл
  результата; превышение → выход с кодом `2` (GitHub Pages не отдаёт файлы
  больше 100 МБ). При чанкованном выводе каждый файл — лишь несколько сотен
  килобайт и лимит практически недостижим.

## 3. Формат файлов данных (`data/`)

Все данные разбиты на **чанки**; клиент узнаёт, какие файлы существуют, из
`manifest.json` (списки `widx`, `packs`, `ru`) и грузит только нужные.
Бакет id вычисляется одинаково на бэкенде (Python `sid // chunk`) и на
клиенте (`bucketOf` в JS) — это обязано совпадать.

### 3.1 `manifest.json` — метаданные сборки

```json
{
  "chunk": 100000,
  "build_date": "2026-11-18 08:00:00 UTC",
  "dump_date": "2026-11-14",
  "source": "https://downloads.tatoeba.org/...",
  "stat": { "eng_with_audio": N, "ru_sentences": N, "links": N,
            "audio_records": N, "word_tokens": N },
  "widx": ["a", "b", ..., "0", "1", ...],
  "packs": [0, 1, 2, ...],
  "ru": [0, 3, ...]
}
```

- `chunk` — размер бакета id (по умолчанию 100000),
- `build_date` — версия данных (используется Service Worker'ом для
  инвалидации кеша, см. §5),
- `widx` — буквы, для которых есть файл индекса,
- `packs` — непустые бакеты английских предложений,
- `ru` — непустые бакеты русских предложений.

### 3.2 `widx/widx_<char>.json` — инвертированный индекс (по букве)

Файл на одну первую букву токена:

```json
{ "hello": [12345, 23456, ...], "help": [...], ... }
```

Токен → отсортированный список английских `sid`, в которых он встречается.
Ключи внутри файла отсортированы (детерминированный вывод).

### 3.3 `packs/pack_<bucket>.json` — пакеты английских предложений

Бакет = `engId // chunk`. Каждый файл — объект с ключами-строками:

```json
{ "12345": {"t": "Hello world.", "a": [100, 200], "l": [67890, 67891]}, ... }
```

- `t` — текст предложения,
- `a` — массив `audio_id` (URL: `AUDIO_BASE + '/' + id + '/file'`),
- `l` — массив русских `sid`-переводов (может быть пустым).

Один пак объединяет то, что раньше было в трёх файлах (`eng.jsonl`,
`audio.json`, `links.json`) — одним запросом клиент получает и текст, и аудио,
и ссылки на перевод.

### 3.4 `ru/ru_<bucket>.jsonl` — русские предложения

JSON Lines, бакет = `ruId // chunk`:

```json
{"id": 67890, "t": "Привет, мир."}
```

Только предложения, на которые ссылаются связи из паков.
```

## 4. Клиентское приложение (`app.js`)

Одно замыкание IIFE, весь код инкапсулирован. Константы:

- `DATA_BASE = './data'` — каталог данных,
- `MANIFEST_URL = './data/manifest.json'` — манифест (версия данных),
- `CHUNK_DEFAULT = 100000` — размер бакета id (перекрывается из манифеста),
- `MAX_PACKS_PER_SEARCH = 6` — максимум пакетов на один поиск,
- `AUDIO_BASE = 'https://api.tatoeba.org/v1/audios'` — база аудио,
- `SEARCH_LIMIT = 20` — размер страницы предложений,
- `FETCH_TIMEOUT_MS = 90000` — таймаут сетевых запросов перевода.

Состояние — единый объект `state` (машина состояний, §4.4); запись с
микрофона держится вне `state`, т.к. это не UI-состояние.

### 4.1 Токенизация и нормализация

**`tokenizeQuery(q)`** — разбиение запроса:

```js
const norm = q.normalize('NFKC').toLowerCase();
const toks = (norm.match(/[0-9a-z']+/g) || [])
  .map((t) => t.replace(/^'+|'+$/g, ''))
  .filter(Boolean);
return [...new Set(toks)];
```

Совпадает с Python-версией (регулярка, апострофы, NFKC, lower-case).
`Set` убирает повторные слова из запроса — если пользователь ввёл
«to be to be», индекс ищется один раз. Числа тоже являются токенами.

**`normalize(s)`** — нормализация для сравнения ответа с эталоном:

1. `NFKC` + `toLowerCase` + `trim`.
2. Уплотнение пробелов: `\s+` → один пробел.
3. Удаление хвостовой пунктуации `.` `!` `?` (одна и более).
4. Замена типографских кавычек `«»“”‘’` на прямые `"` и `'`.
5. Замена `-`/`–`/`—` с пробелами вокруг на одиночный пробел
   (`smth - else` ≡ `smth else`).

Это даёт толерантность к регистру, кавычкам, концевому знаку и пробелам
вокруг тире.

### 4.2 Загрузка данных (чанки, лениво, кэшировано)

Никаких монолитов: клиент знает только `manifest.json` и подтягивает чанки по
мере надобности. Каждый ресурс имеет кэш-объект (`cache`) и промис
(`pending`), чтобы параллельные вызовы не дублировали загрузку:

| Функция             | Что грузит                                  | Клиентское представление          |
|---------------------|---------------------------------------------|-----------------------------------|
| `ensureManifest()`  | `manifest.json?check=`                      | `manifest`, `chunk`               |
| `ensureWidxChar(c)` | `widx/widx_<c>.json`                        | `Object(token → [engIds])`        |
| `ensurePackBucket(b)` | `packs/pack_<b>.json`                     | `Map(string engId → {t,a,l})`     |
| `ensureRuBucket(b)` | `ru/ru_<b>.jsonl`                           | `Map(ruId → text)`                |
| `packEntry(id)`     | бакет этой id (+ содержимое)                | `{t,a,l}` или `null`              |

При ошибке промис сбрасывается (`delete pending[key]`), чтобы следующая
попытка загрузила заново. `ensureManifest` использует URL с `?check=` —
Service Worker проверяет версию данных и чистит кеш при изменении (§5).

### 4.3 Поиск (`performSearch`)

Ключевой локальный алгоритм:

```
resetPool()
await ensureManifest()                          // версия + chunk
tokens = tokenizeQuery(q)                       // без дубликатов
для первой буквы каждого токена → ensureWidxChar (параллельно)
cands = null
для каждого tok из tokens:
    list = widxCache[первая буква]?.[tok]      // список со словом
    если list нет → поиск неудачен (return false)
    cands = пересечение(cands, list)           // ∩ по всем словам запроса
если cands пуст → return false

группировка cands по бакетам (byBucket) + сортировка по убыванию
await fillPool(SEARCH_LIMIT)                   // грузит паки по bucketOrder
return pool.length > 0
```

**Приоритет бакетов (`refillWindow`)** — ключевая оптимизация трафика. Вместо
загрузки паков всех кандидатов (для частых слов это десятки бакетов)
кандидаты группируются по бакетам, бакеты сортируются по убыванию числа
кандидатов, и пакеты загружаются по одному, пока не наберётся достаточно
кандидатов или не исчерпан лимит `MAX_PACKS_PER_SEARCH` (6):

```
byBucket: id → бакет (id // chunk)
bucketOrder = бакеты по убыванию |кандидатов|; bucketPos = 0
refillWindow():
    пока bucketPos < bucketOrder.length и packsLoaded < 6:
        загрузить pack_<bucket>; packsLoaded++
        тиры: withRu = id с непустым l, withoutRu = остальные
        candQueue += shuffle(withRu) + shuffle(withoutRu)
        если candQueue накопил ≥ pool.length + SEARCH_LIMIT → break
    вернуть (добавлено ли что-то)
```

Бакеты с наибольшим числом кандидатов отдаются первыми — обычно хватает
1–5 паков. `refillWindow` возвращает `added > 0`, поэтому когда лимит паков
исчерпан, но бакеты ещё остались, бесконечного цикла не возникает.

Объём данных, скачиваемых на один поиск: 1 файл widx (до ~9 МБ на самую
частую букву `t`) + 1–5 паков + при необходимости 1–3 ru-чанка. Повторные
поиски тех же букв/бакетов не качают ничего нового (кэши в памяти + SW).

**Пересечение**: первый список сохраняется как есть, для каждого следующего
токена строится `Set`, и текущий список фильтруется по нему
(`cands.filter(id => set.has(id))`) — O(n·m) суммарно.

**Деление на два тира**: предложения **с русским переводом** идут первыми
(они качественнее для тренажёра — пользователь переводит с русского на
английский), при этом внутри каждого тира — **случайный порядок**
(`shuffle`, Фишер—Йейтс). Предложения без русского перевода — запасные,
попадают в конец очереди.

**`fillPool(target)`** — асинхронная пагинация по бакетам:

```
пока pool.length < target:
    если candIdx >= candQueue.length:
        if (!await refillWindow()) break   // новый пак из bucketOrder
    id = candQueue[candIdx++]
    если id уже видали (seenIds) → пропустить
    item = await buildLocalItem(id)        // если предложение «собираемое»
    если item нет → пропустить
    seenIds.add(id); pool.push(item)
```

`buildLocalItem(id)` (async) проверяет три факта: текст существует (`e.t`),
есть аудио (`e.a` → непустой массив), находит первый русский перевод по `e.l`
(для текста перевода лениво подгружается ru-чанк бакета; сбой одного перевода
не роняет пункт — пробуется следующий). Если русский перевод отсутствует —
`ruText = null`, `auto = true` (пойдёт машинный перевод, §4.6).
Если аудио нет — пункт в пул не попадает вообще.

**Результат поиска** — заполненный пул из ≤ 20 пунктов. Если пул пуст —
поиск считается безуспешным («Ничего не найдено»).

### 4.4 Машина состояний и пагинация

`state.step` − одно из:

| step       | Экран                                           |
|------------|-------------------------------------------------|
| `word`     | форма ввода слова                               |
| `loading`  | поиск (спиннер), все элементы управления блокируются |
| `exercise` | показано русское предложение, ждём ответа       |
| `revealed` | показан эталон + сравнение + аудио              |

**`onSearch`** — ввод с клавиатуры/кнопка «Найти»: проверка непустого
запроса, переход в `loading`, `performSearch`; при успехе — `cursor = 0`,
`resetExercise()`, `exercise`.

**`onNext`** — «Следующее предложение» (асинхронный; `loadingMore`
блокирует повторный вход и кнопку):

```
если идёт дозагрузка (loadingMore) → ignore
если cursor+1 < pool.length → cursor++, resetExercise()
иначе:
    before = pool.length
    loadingMore = true
    await fillPool(pool.length + SEARCH_LIMIT)   // догрузка чанками
    loadingMore = false
    если пул вырос → cursor = before, resetExercise()
    иначе → ошибка «Предложения закончились» с кнопкой Повторить
```

Так что «бесконечная лента» в пределах одного поиска ограничена числом
кандидатов. `seenIds` защищает от повторов: одно и то же предложение не
появится дважды в одном поиске; при новом поиске `resetPool()` очищает всё.

**`onNewWord`** — полный сброс к начальному экрану (`word`).

**`resetExercise`** — сброс состояния упражнения: очистка ответа, `revealed`,
индекса аудио, грамматики, остановка аудио, сброс записи, скрытие хинтов.

### 4.5 Проверка ответа и грамматика (harper.js)

**`onCheck`** (Проверить):
- сохранить `userAnswer`, `step = 'revealed'`, `grammar = { checking }`,
- `playApiAudio()` — озвучить это предложение сразу,
- `runGrammarCheck()` — параллельно начать линтер.

**`runGrammarCheck`**:

```
item = currentItem(); text = userAnswer
token = ++grammarToken                        // защита от гонки
если нет item или text пуст → grammar = idle

your = normalize(text); correct = normalize(item.enText)
если your === correct → return (метка «match», линтер не нужен)

grammar = {status:'checking'}; render
linter = await loadHarper()                  // lazy import WASM
если token !== grammarToken → return         // ответ уже устарел
lints = await linter.lint(text, {language:'plaintext'})
если token !== grammarToken → return
grammar = {status: lints.length ? 'errors' : 'ok', lints}
```

**Токен гонки** (`grammarToken`): если пользователь сменил предложение или
нажал «Повторить», старое асинхронное lint-выполнение «пропадает» — токен
не совпадает, результат отбрасывается, а память объектов lints очищается
`freeGrammar()` (harper.js аллоцирует WASM-память для каждого инспектора).

**`loadHarper`** — динамический `import()` обоих JS-модулей harper
(`vendor/harper/index.js`, `vendor/harper/binary.js`), сборка
`new WorkerLinter({ binary })` и `await linter.setup()`. Промис общий
(`harperLoadPromise`): линтер создаётся один раз, второй вызов переиспользует
его. WASM весит ~20 МБ, поэтому загрузка отложена до первого ответа.

**Классификация результата** в `renderState`:

- `match` — нормализованный ответ совпал с эталоном;
- `near` — не совпал, но грамматика **без ошибок** (`ok`) — «близко»;
- `mismatch` — не совпал и есть ошибки / линтер недоступен / ещё не
  завершён (`idle`);
- `checking` — линтер ещё работает (показывается «Проверяем грамматику…»).

`yourCell` (кликабельная ячейка) открывает `openLintDialog()` — модальное
окно «Ошибки в вашем ответе» со списком lint-сообщений и проблемных
фрагментов (`lint.message()`, `lint.get_problem_text()`).

**`onRetryAnswer`** — «Повторить»: `resetExercise()`, снова `exercise`.

### 4.6 Машинный перевод (fallback для предложений без русского)

Когда `buildLocalItem` не нашёл русский перевод (`ruText = null`) — текст
помечается `auto = true`, и включается `prefetchTranslation(item)`.

**`translateRu(en)`** — двухуровневый fallback с кешем localStorage:

1. `cachedRu(en)` — ключ `enru:<текст>`, если есть → отдать без сети;
2. Google GTX: `translate.googleapis.com/translate_a/single?client=gtx&sl=en&tl=ru&dt=t&q=...`
   — ответ-массив, `parseGtx` склеивает сегменты `data[0][i][0]`;
3. MyMemory API: `mymemory.translated.net/get?q=...&langpair=en|ru`
   — `parseMyMemory` читает `responseData.translatedText`;
4. Успех → `storeRu` в localStorage (кеш).

Всё через `fetchTimeout` (AbortController, 90 с) — зависший перевод не
заблокирует интерфейс.

**`prefetchTranslation(item)`**:

- запускается в `renderState()` для текущего предложения и для следующего
  (`state.pool[cursor+1]`) — перевод готовится заранее,
- повторно не запускается: флаги `item.pending` / `item.failed` / наличие
  `ruText` прерывают повторную попытку,
- по завершении: если предложение всё ещё текущее (currentItem()) —
  `renderState()` обновит экран; переключение на следующее предложение
  перерисует, когда оно станет текущим.

### 4.7 Аудио носителя

**`buildLocalItem`** формирует `audios: [...]` — список URL
`https://api.tatoeba.org/v1/audios/{id}/file`.

**`playApiAudio`**:

- если записей нет или всё перепробовано (`preloadFailed`) →
  `audioUnavailable = true`, ошибка «Аудио недоступно»;
- `audioIndex` — индекс текущей записи; при превышении сбрасывается в 0;
- `loadApiAudio(url)` ставит `src`/`load()` только если URL сменился или идёт
  повторная попытка (`audioRetries > 0`);
- `playWhenReady()` — `play()` вызывается только когда медиа готово
  (`readyState >= 2`) либо по событию `canplay`; крайний срок — 8 с (таймаут),
  чтобы не зависнуть навечно. Отклонённый `play()` (политика
  автовоспроизведения) → хинт «Нажмите „Произношение (носитель)“…».

**`preloadApiAudio`** — вызывается в `renderState()` для текущего пункта на
шаге `exercise` (до reveal). Помечает `preloadMode = true` — значит,
фоновый preload, а не активное желание проиграть.

**`onApiAudioError`** (событие `error` на `apiAudio`):

```
audioRetries++                      // счётчик ошибок текущей записи
если audioRetries <= AUDIO_MAX_RETRIES (2):
    через AUDIO_RETRY_DELAY_MS (400 мс) — перезапустить ТУ ЖЕ запись
    (предмет остается тем же, иначе забросить)
иначе:
    audioRetries = 0
    audioIndex++                    // перейти к следующей записи
    если осталась следующая запись:
        preloadMode ? preloadApiAudio() : playApiAudio()
    иначе:
        preloadFailed = true
        если preloadMode → просто перерисовать (тихая неудача на этапе exercise)
        иначе → audioUnavailable = true, навязчивая ошибка
```

Почему ретраи: самое частое проявление «аудио не играет при первом
нажатии» — транзиентная ошибка холодного соединения к `api.tatoeba.org`
(первый визит, DNS/TLS не прогреты, конкуренция с загрузкой `data/` и
WASM-линтера). Раньше единственная ошибка навсегда списывала запись
(`audioIndex++` без повтора того же URL). Теперь:
- каждая запись получает до 2 повторов с паузой 400 мс того же URL;
- счётчик сбрасывается событием `canplay` (загрузка реально удалась);
- по исчерпании повторов запись меняется (по-прежнему с «тихим» режимом
  на этапе exercise и «навязчивым» при игнорируемом reveal).

Итого **единый алгоритм «повтори текущую запись, потом перебирай по
очереди»** работает двумя режимами: тихим (preload до ответа) и активным
(после ответа).

**`stopApiAudio`** — пауза, сброс `src`, `load()`.

### 4.8 Запись с микрофона

`startRecording`:

1. Проверка поддержки `getUserMedia`/`MediaRecorder`.
2. `enumerateDevices` → нет аудио-входа → понятное сообщение.
3. `getUserMedia({audio:true})` с разбором типов ошибок
   (`NotAllowedError`, `NotFoundError`, `NotReadableError`, `SecurityError`,
   `AbortError`) на русские сообщения с действиями.
4. Выбор MIME-типа из `RECORD_MIME_CANDIDATES` первым поддерживаемым
   (`webm;codecs=opus` → `mp4;codecs=mp4a.40.2` → `mp4` → `ogg;codecs=opus`).
5. `MediaRecorder`; `ondataavailable` собирает chunk'и; `onstop` создаёт
   `Blob`, объектный URL в `state.recording`, озвучивает в `myAudio`.
6. Токен `recorderToken` — защита от гонки между стопами: `onstop` проверяет
   `state.recorderToken === token` (иначе это запись, поверх которой
   начали новую/сбросили).

`finishRecording` — `recorder.stop()` → триггерит `onstop` (Blob создаётся
именно там).

`discardRecording` — инкремент токена (аннулирование ожидающего `onstop`),
остановка всех треков, отзыв объектного URL, чистка.

`onPlayMine` — проигрывание собственной записи; при отклонённом промис —
хинт.

### 4.9 Рендер (`renderState`)

Единая функция рисования по `state` — вызывается после каждого изменения
состояния. Определяет:

- видимость панелей по `step` (word/loading/exercise/revealed, ошибка);
- заголовок `query-word` (запрос — пустой на шаге `word`);
- русский текст (`ruText` / «Переводим…» / «Перевод недоступен») и бейдж
  `*автоперевод*` при `auto`;
- `<audio>` для текущего пункта (`preloadApiAudio`) и **предзагрузку
  перевода следующего** пункта (`prefetchTranslation(state.pool[cursor+1])`);
- шаг `revealed`: сравнение ответов, классы `match/near/mismatch`, хинт
  «Проверяем грамматику…», кликабельность `yourCell`;
- кнопки аудио/записи (disabled по `audioUnavailable`, текст кнопки записи
  по `recordingActive`);
- панель ошибок с кнопкой «Повторить» если `retry`.

## 5. Service Worker (`sw.js`)

Две роли с разными стратегиями:

**install**: `cache.addAll(SHELL)` — прекешируется остов приложения
(корень, `index.html`, `styles.css`, `app.js`, манифест, иконки). Данные
не прекешируются (пусть даже чанками — их сотни, клиент сам выбирает нужные).

**activate**: удаляются все старые кеши, кроме текущего shell-кеша
(`tatoeba-shell-v4`) и общего кеша данных (`tatoeba-data-v1`) —
мгновенное обновление после перехода на новую версию приложения.

**fetch**: только same-origin GET; ветвление по URL:

| Запрос                        | Стратегия                                         |
|-------------------------------|---------------------------------------------------|
| остов (shell)                 | Stale-While-Revalidate                            |
| `/data/manifest.json?check=`  | network-first + сравнение версии + чистка кеша    |
| остальное `/data/...`         | cache-first                                       |

**Shell (SWR):**

```
cached = caches.match(request)
fresh = fetch(request):
    если статус 200 → cache.put(request, copy)   // обновить кеш
    при сетевой ошибке → вернуть cached
return cached || fresh
```

**Данные (cache-first):**

```
cached = caches[DATA_CACHE].match(request)
если есть → вернуть cached               // сети не трогаем
иначе fetch → при 200 положить в кеш → вернуть
```

Полный набор данных клиент больше не тянет ни при install, ни при первом
заходе — чанки попадают в кеш по одному, по мере реального использования.
Повторные заходы не скачивают ничего из уже использованных букв/бакетов.

**Проверка версии (`manifest.json?check=`):** приложение при старте и перед
поиском делает запрос к манифесту с `?check=` — единственный запрос в сети
за заход (2–3 КБ с заголовками). SW:

1. читает свежий манифест из сети (`cache: 'reload'`);
2. сравнивает `build_date` со значением из кешированной копии;
3. если версия изменилась — **очищает весь кеш данных** (чанки
   перекачаются по мере надобности), затем обновляет кешированную копию
   манифеста;
4. если сеть недоступна — возвращает кеш как есть (офлайн-режим).

Так смена данных на сервере не требует от пользователя ничего: старые чанки
инвалидируются одним маленьким запросом.

Note: `guide.html` не входит в SHELL, но SWR кеширует его при первом
переходе; для полной офлайн-навигации его можно добавить в массив.

## 6. Тема оформления

Реализована в `index.html` (встроенный скрипт), без участия `app.js`:

- режимы: `system` (по умолчанию) → `dark` → `light` (циклически кнопкой
  «Тема: …» в подвале),
- выбор хранится в `localStorage` ключ `tatoeba-theme`,
- `apply(mode)`: выставляет атрибут `data-theme` на `<html>` (стили в
  `styles.css` реагируют), меняет `<meta name="theme-color">`;
- подписка на `matchMedia('(prefers-color-scheme: dark)')` — авто-режим
  живёт при переключении темы ОС.

## 7. Структура репозитория и деплой

```
tatoeba5/
├── index.html            # SPA-каркас, тема, регистрация SW
├── app.js                # вся логика приложения
├── styles.css            # стили (светлая/тёмная темы)

├── sw.js                 # service worker (shell SWR + данные cache-first)
├── manifest.webmanifest  # PWA-манифест
├── start.bat             # локальный запуск (Python http.server)
├── tools/build_index.py  # сборщик data/
└── data/                 # сгенерированные данные (коммитятся)
    ├── manifest.json     # версия, chunk, списки чанков
    ├── widx/widx_<c>.json    # индекс по первой букве токена
    ├── packs/pack_<b>.json   # предложения: текст, аудио, переводы
    └── ru/ru_<b>.jsonl       # русские предложения
├── vendor/harper/        # локальный harper.js (WASM)
└── icons/                # иконки PWA
```

Публикация — простая: `git push` в ветку `main` репозитория
`ru2eng/ru2eng.github.io`, GitHub Pages раздаёт файлы как есть.
Важно:

- Клиент **не скачивает всё сразу**: за один поиск — один widx-чанк +
  несколько паков/ru-чанков. Данные копятся в кеше SW по мере использования.
- Лимит Pages — 100 МБ **на файл**; самые большие чанки (~9 МБ) далеки от
  него (§2.5). Суммарный объём каталога ~140 МБ на хранение в репозитории
  — это допустимо, т.к. лимит пофайловый.

## 8. Часто пересматриваемые места

- **Совместимость индекса и запроса**: правки в `tokenize_key` (Python)
  обязательно синхронизировать с `tokenizeQuery` (JS) — расхождение
  сломает поиск.
- **Совместимость бакетов**: формула `id // chunk` совпадает в
  `build_index.py` и в `bucketOf()` (JS). При изменении `--chunk-size`
  обе стороны синхронизировать, иначе паки не найдутся.
- **Лимиты данных**: при расширении диапазона слов в сборщике сначала
  проверяй `HARD_LIMIT` (§2.5) — самый большой чанк ~9 МБ, запас есть.
- **Аудио**: список `audios` строится из `e.a` пакета; при добавлении
  нового источника записей — менять только `buildLocalItem` и
  `onApiAudioError` (алгоритм выборки общий). Повторы задаются константами
  `AUDIO_RETRY_DELAY_MS` и `AUDIO_MAX_RETRIES` в `app.js`.
- **Гонки**: три независимых токена — `grammarToken` (линтер),
  `recorderToken` + `state.recorderToken` (запись), а загрузка чанков
  дедуплицируется промисями `*Pending` (each chunk). Все асинхронные
  завершения проверяют актуальность перед `renderState()`.
